\subsection{Lexer and Symbol Table}
The lexer was verified manually by running the full pipeline and inspecting
Stage~1 token output for programs that exercise every token category: integer
and float literals, Boolean literals, string literals, the five reserved keywords,
two-character comparison operators (\texttt{==}, \texttt{!=}), single-character
operators, and delimiters. Identifier scanning with keyword fallback was
confirmed by checking that \texttt{true} and \texttt{false} are emitted as
\texttt{BOOL\_LITERAL} tokens, the five reserved words (\texttt{if},
\texttt{else}, \texttt{while}, \texttt{def}, \texttt{return})
as their respective keyword token types, and ordinary names including
\texttt{print} as \texttt{IDENTIFIER} tokens. For example, the source fragment \texttt{x = 10;}
produces the token sequence:

\begin{lstlisting}
IDENTIFIER  'x'    line=1 col=1
ASSIGN      '='    line=1 col=3
INT_LITERAL '10'   line=1 col=5
SEMICOLON   ';'    line=1 col=7
\end{lstlisting}

Error paths were also checked: supplying a bare \texttt{!} character raises a
\texttt{LexerError} with a source position and a message suggesting
\texttt{!=}, and an unterminated string literal raises a \texttt{LexerError}
citing the opening line.

The symbol table was verified through the type checker and the Stage~4 output.
Duplicate variable definitions were confirmed to raise a
\texttt{SymbolTableError} before execution. Scope isolation was verified with
nested blocks: a variable defined inside an \texttt{if} or \texttt{while} body
is not visible in the outer scope after the block ends. The
\texttt{format\_table()} output was checked against the expected column layout
(name, kind, type, initialisation status, parameters) for both variable and
function symbols.

\subsection{Parser, Parse Tree, and AST}
The parser was verified manually by running the full pipeline and inspecting
both the Stage~2 parse-tree output and the Stage~3 AST output. The following
cases were checked:

\begin{itemize}
    \item the parse-tree view contains grammar-oriented labels such as \texttt{program}, \texttt{statement}, \texttt{assignment}, and \texttt{expr},
    \item arithmetic expressions with mixed precedence (e.g.\ \texttt{x + y * 2}) place multiplication in a deeper subtree than addition,
    \item \texttt{x = 5;} produces an \texttt{Assign} node, while \texttt{add(1,2);} produces a statement-level \texttt{FunctionCall}, confirming the IDENTIFIER+ASSIGN lookahead,
    \item \texttt{if} with and without an \texttt{else} clause yields an \texttt{If} node whose \texttt{else\_block} is present only when required,
    \item function definitions store only parameter names in \texttt{FunctionDef}, with no type annotations at this stage,
    \item string literals in \texttt{Literal} nodes have surrounding double-quotes stripped, while runtime output restores them for \texttt{String} values,
    \item missing semicolons, unmatched parentheses, and unexpected tokens all produce source-positioned \texttt{ParseError} messages.
\end{itemize}

\subsection{Arithmetic Expressions}
Arithmetic expressions were tested with integer-only and float-only programs to
verify operator precedence and strict type separation. The expression
\texttt{x + y * 2} confirmed that multiplication binds more tightly than
addition, and mixing integer and float operands correctly produced a type error,
confirming the no-overloading design. The test suite explicitly verifies that
mixed-type arithmetic is rejected:

\begin{itemize}[nosep]
  \item \texttt{1 + 2} --- valid Integer arithmetic.
  \item \texttt{2.0 +. 3.5} --- valid Float arithmetic.
  \item \texttt{5.0 -. 1.5}, \texttt{2.0 *. 3.0}, \texttt{9.0 /. 4.0} --- valid Float arithmetic for the other dot-suffixed operators.
  \item \texttt{1 + 2.5} --- \texttt{TypeError}: operator \texttt{+} requires two Integer operands.
  \item \texttt{2 +. 3} --- \texttt{TypeError}: operator \texttt{+.} requires two Float operands.
  \item \texttt{10 / 0} and \texttt{10.0 /. 0.0} --- \texttt{InterpreterError}: division by zero, raised at runtime.
  \item \texttt{1.0 +. 2.0 *. 3.0} --- evaluates to \texttt{7.0} confirming \texttt{*.} binds more tightly than \texttt{+.}.
\end{itemize}

These rejection tests are the primary evidence for the no-overloading
requirement. In a promotion-based language, \texttt{1 + 2.5} and
\texttt{2 +. 3} would silently succeed; here, both are rejected as
\texttt{TypeError}s, showing that each operator token has a single fixed type
signature and that no implicit coercion occurs. The suite includes 7 dedicated
mixed-type and wrong-type operator tests (Table~\ref{tab:test-summary},
\texttt{TypeCheckerTests}), so this guarantee is verified mechanically rather
than asserted informally.

\subsection{Boolean Expressions}
Boolean expressions were tested inside \texttt{if} and \texttt{while}
conditions. The type checker correctly enforced that both operands of
\texttt{==} and \texttt{!=} must be arithmetic; supplying a \texttt{Boolean}
or \texttt{String} operand produced a source-positioned \texttt{TypeCheckError}
before any execution.

\subsection{Assignment Statements}
Assignments were tested for first-use type inference and reassignment
consistency. For example, assigning \texttt{5} and then \texttt{"hello"} to
the same variable correctly produced a type error, confirming that the inferred
type is fixed after the initial binding.

\subsection{If-Then-Else}
Conditional programs were constructed to verify that exactly one branch
executes for a given condition and that neither branch is entered when the
condition evaluates to the opposite truth value. Non-Boolean conditions were
also supplied and confirmed to be rejected by the type checker before
execution.

\subsection{While-Loop}
While-loops were tested with an integer countdown from three to zero. The
results confirmed that the loop body executes once per iteration and
terminates when the condition becomes false, with \texttt{print()} producing
one output line per pass rather than accumulating output until loop exit.

\subsection{Functions}
Function tests covered value parameter passing (call-by-value), local scope
execution, and return value propagation. For called functions, the type
checker correctly fixed parameter types from the first call site and enforced
that signature for all subsequent calls to the same function.

\subsection{Print}
The built-in \texttt{print()} function was tested with all supported runtime
types. The output includes the printed value together with its type, such as
\texttt{3.14 : Float} and \texttt{"plc" : String}.

\subsection{Unary Minus}
The unary minus operator was verified for integer literals (\texttt{x = -5}),
float literals (\texttt{y = -. 3.14}), negated float variables
(\texttt{y = -. x}), negated integer variables (\texttt{y = -x}), and
negation inside a larger expression (\texttt{x = 3 + -2}). In each case the
type checker assigned the correct type and the interpreter produced the
expected value. Note that float negation uses the \texttt{-.} token, consistent
with the Caml~Light convention; using plain \texttt{-} on a \texttt{Float}
operand is rejected by the type checker.

\section{Type Error Detection}
The checker was verified with invalid programs involving incompatible
assignment, invalid arithmetic operands, wrong function arguments, and
non-Boolean conditions. In each case the system stopped before execution and
reported a source-positioned type error. Representative error messages are
shown below.

\begin{lstlisting}
# Assignment type mismatch
[line 2, col 1] TypeError: Cannot assign String to variable 'x' of type Integer

# Non-Boolean if condition
[line 1, col 4] TypeError: If condition must have type Boolean

# Wrong argument type for function
[line 5, col 9] TypeError: Argument 1 of 'add' must be Integer, got String
\end{lstlisting}

\section{Automated Test Suite}
The automated regression suite is located in \texttt{tests/test\_pipeline.py}
and uses Python's built-in \texttt{unittest} framework. The tests are
organised into five classes, each targeting a distinct compiler stage.

\begin{table}[H]
\centering
\caption{Automated test coverage by class}
\label{tab:test-summary}
\begin{tabular}{llr}
\toprule
Test class & Stage covered & Tests \\
\midrule
\texttt{LexerTests}        & Tokenisation (\texttt{lexica.py})                &  12 \\
\texttt{SymbolTableTests}  & Scoped symbol table (\texttt{symbol\_table.py})  &   7 \\
\texttt{ParserTests}       & Parsing, precedence, parse-tree/AST output        &   7 \\
\texttt{TypeCheckerTests}  & Static type inference (\texttt{type\_checker.py}) &  22 \\
\texttt{IntegrationTests}  & Full pipeline execution                           &  29 \\
\midrule
                           & \textbf{Total}                                   & \textbf{77} \\
\bottomrule
\end{tabular}
\end{table}

\noindent\textbf{LexerTests} verify that each token category (integer, float,
Boolean, string, keywords, identifiers, two-character operators, and the four
float-arithmetic operators \texttt{+.} \texttt{-.} \texttt{*.} \texttt{/.})
is produced correctly, that float literals such as \texttt{3.14} are not
confused with integer followed by a dot operator, that source line numbers are
tracked across newlines, and that illegal characters and unterminated strings
raise \texttt{LexerError}.

\noindent\textbf{ParserTests} verify structural correctness of parsing. The 7
tests cover missing-semicolon and unclosed-brace error reporting, integer and
float operator precedence, left-associativity, parenthesised expressions
overriding precedence, and availability of both parse-tree and AST renderings
in the pipeline result.

\noindent\textbf{SymbolTableTests} exercise the symbol table directly, without
going through the full pipeline. They cover variable definition and lookup,
duplicate definitions for variables and functions, parent-scope lookup through
\texttt{child\_scope()}, undefined-symbol errors, and \texttt{format\_table()}
output for variable and function rows.

\noindent\textbf{TypeCheckerTests} verify static type inference and error
detection. The 22 tests cover integer and float arithmetic, integer floor
division, strict type separation, string and Boolean type inference, assignment
type mismatch, non-Boolean conditions, undefined variables, wrong argument
count and type, and uncalled-function body checking for both invalid and valid
cases.

\noindent\textbf{IntegrationTests} run programs through multiple pipeline
stages and verify final output. Cases include unary negation on all numeric
types, division by zero for both \texttt{/} and \texttt{/.}, both branches of
\texttt{if}/\texttt{else}, while-loop countdown, \texttt{print()} with every
type, value-parameter isolation, nested function calls, comparison results
assigned and printed directly, variable reassignment, scope isolation, rejection
of passing a void-returning function to \texttt{print()}, and rejection of a
function with a non-total \texttt{return}.

The tests can be run with:

\begin{lstlisting}
# macOS / Linux
python3 -m unittest discover -s tests -v

# Windows
python -m unittest discover -s tests -v
\end{lstlisting}

All 77 tests pass.

\section{Error Handling}
The language system reports errors at four stages:

\begin{itemize}
	\item lexical errors for malformed characters or unterminated strings,
	\item parse errors for invalid syntax such as missing semicolons,
	\item type errors for programs that violate static typing rules,
	\item runtime errors for division by zero and other execution failures.
\end{itemize}

All error messages include a source position in the form
\texttt{[line~X, col~Y]} to aid debugging.

\section{Limitations and Future Work}
The implemented language intentionally restricts several advanced
programming-language features to focus on core compiler construction
principles and static type inference.

The current implementation does not support recursive functions, arrays,
records, polymorphic typing, closures, or garbage collection. Type inference
is syntax-directed and deterministic rather than based on full unification
algorithms such as Hindley--Milner inference. The execution model is
interpreted directly from the AST rather than compiled into bytecode or
machine code.

Future extensions may include recursive function support, richer data
structures, additional control-flow constructs, optimisation passes, and
compilation to a lower-level intermediate representation.
